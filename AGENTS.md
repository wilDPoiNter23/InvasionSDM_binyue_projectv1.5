# Project file-placement and publication rules

Read this file before every repository task. Follow existing project instructions
and the author's current task. More specific scientific instructions remain in
force. This file establishes placement rules; it does not authorise new analyses.

## Author-supplied rules

> Keep the environment-only production workflow in:
> code/10_sensitivity/environment_only/
>
> All scientifically meaningful project scripts should remain within the main
> code hierarchy.
>
> Do not create a separate supplementary_code tree.
>
> Historical variants may live in stage-specific subdirectories such as:
> code/04_sdm/variants/
> code/04_sdm/repairs/
> code/05_invasion_suitability/variants/
>
> All public comments, headers and notes must be concise natural English.
>
> Do not use AI/Codex/agent/audit/recovery language in public-facing files.

The author's repository checker requirements are:

- new scripts or data files must not be placed in the repository root;
- an unapproved top-level directory must not be created;
- filenames must not contain final2, final_final, new_final, copy or latest_version;
- public-facing text files must not contain Chinese;
- public-facing files must not contain private Windows or HPC absolute paths;
- public-facing files must not contain AI, Codex, agent, forensic audit or generated by;
- tracked files must not include .Renviron, model objects, rasters, raw data or logs.

Exclude AGENTS.md itself from the AI/Codex-word check because it must describe
the rules. This exception does not exempt Chinese text or private absolute paths.

## Placement map

Approved top-level directories are code, config, docs, examples, metadata,
scripts, tools, working and zenodo. No other top-level directory is approved.

| Location | Purpose |
| --- | --- |
| code/01_data_preparation through code/10_sensitivity | Scientific scripts in their existing workflow stages |
| code/10_sensitivity/environment_only | Environment-only production workflow |
| config | Portable configuration templates; config.local.R stays private and ignored |
| docs | Public workflow, input requirements and reproduction documentation |
| metadata | Approved provenance manifests, species roster and variable dictionaries |
| scripts | Repository layout checker and repository maintenance commands |
| tools | Existing static publication validation tools |
| examples | Small curated usage examples; no original data or model outputs |
| zenodo | Data-package instructions and staging manifest; no large assets |
| working | Ignored private task notes, plans, inspection records and scratch work |
| External paths configured by the user | Raw inputs, models, rasters, results and run logs |

Only README.md, CITATION.cff, AGENTS.md, .gitignore, .gitattributes and a verified
LICENSE or LICENSE.md may be root files. Do not invent licence terms.
Do not write scripts, tables, run outputs or task notes at the root.

The currently approved tracked tables are:

- metadata/archived_source_checksums.csv
- metadata/city_variables.csv
- metadata/hpc_environment_observed_20261013.csv
- metadata/predictor_list.csv
- metadata/species_list.csv
- zenodo/zenodo_manifest.csv

New public tables require explicit author approval and a corresponding checker
allowlist update. Moving a raw table into a documentation directory does not
make it publishable. Preserve the meaning and schema of existing approved tables.

## Mandatory check on every repository task

Run from the repository root, including before committing and after changes:

```sh
python scripts/check_repository_layout.py
```

Report the command's actual exit status. A nonzero result is a failed check;
resolve the issue within the authorised scope or report it. Never weaken checks
or add exceptions merely to obtain a pass. The checker examines indexed and
non-ignored pending files; root entries are checked even when ignored. Private
working notes are excluded from public-text checks only while untracked.

For relevant scientific source changes, also run the existing static publication
validator with the configured Rscript and Bash executables. Static validation
does not establish numerical reproduction or scientific acceptance.

## Preservation and task boundaries

Do not move existing scientific files in this task. Do not modify analysis
formulas. Do not delete anything. Do not merge to main.
Keep original source-checksum records and scientific lineage intact. Existing
files outside the intended layout remain in place until the author explicitly
authorises a separate migration. Future tasks must follow their own explicit
authorisation before rerunning models, deleting assets, publishing or merging.
Use external configuration instead of personal absolute paths in public files.
Do not create duplicate code trees or competing manifests. Reuse the relevant
existing stage directory and update its documentation when authorised.
